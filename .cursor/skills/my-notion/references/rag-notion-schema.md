# RAG 友善的 Notion Schema 參考

來源： [建立人機協作／RAG 友善的 Notion 資料庫 Schema](https://app.notion.com/p/3c6bde09f6fe815c8c13dcbf2c8beefe)

這份參考整理來源頁面的設計原則。它是決策指南，不是每個 Database 都必須照抄的固定欄位表。

## 設計目標

Schema 同時服務三種工作：

1. 人類能快速瀏覽、篩選與維護。
2. AI 能用明確 metadata 搜尋、理解與關聯資料。
3. 未來作為 RAG／知識庫來源時，資料能被搜尋、追溯與驗證。

精簡優先：每個欄位都必須有明確的查詢、分類、關聯或治理用途；只為了看起來完整而增加欄位會降低資料品質。

## 欄位決策表

| 欄位 | 建議 Notion 類型 | 何時使用 | RAG／治理價值 |
| --- | --- | --- | --- |
| 名稱 | Title | 每筆資料都需要 | 讓資料脫離列表後仍可理解 |
| 摘要 | Rich text | 需要快速判斷內容相關性 | 提供 1–3 句的檢索前摘要 |
| 類型／分類 | Select | 分類值穩定且需要篩選 | 讓查詢條件一致 |
| 標籤／關鍵字 | Multi-select 或 Rich text | 一筆資料可屬於多個主題 | 補足分類無法涵蓋的搜尋詞 |
| 狀態 | Status 或 Select | 需要生命週期、啟用或封存判斷 | 避免把草稿或過期資料當成有效知識 |
| 來源 | URL 或 Rich text | 需要回到原始文件、網站或紀錄 | 支援引用、追溯與人工核驗 |
| 負責人／建立者 | People | 需要協作、審核或責任歸屬 | 讓缺口有明確處理人 |
| 相關資料 | Relation | 有專案、任務、文件、客戶等實體關係 | 比純文字連結更可查詢與維護 |
| 最後更新 | Last edited time 或 Date | 資料可能過期 | 判斷新鮮度與重新審查時機 |
| 審核狀態 | Status 或 Select | AI 生成、重要知識或外部資料需要人工確認 | 區分候選內容與可採信內容 |
| 唯一識別碼 | Unique ID 或文字 | 需要 API、同步或跨系統引用 | 降低同步與關聯歧義 |

以上欄位依情境選用，不要預設全部建立。若詳細內容很長，保留在 page body；屬性只保存可用於篩選、排序、查詢與關聯的 metadata。

## 型別與內容原則

- Select 是有限且穩定的枚舉；Multi-select 是多主題標籤；Relation 是實體間關係。
- 不要以多個文字欄位複製同一個概念，也不要以文字 URL 取代應使用的 Relation。
- 每筆資料應能獨立理解，避免只寫「這個」、「上述」或「同前」。
- 欄位名稱應固定、清楚並具語義；同一概念在不同 Database 不要任意改名。
- 可能過期的資料至少要有來源、更新時間或有效狀態中的適當組合。
- AI 生成或尚未查證的資料，應保留可辨識的審核狀態；未完成驗證前不能當成已核准知識。

## 設計檢查

建立 Database 前，確認以下問題都有答案：

- 人類會如何找資料、排序資料與維護資料？
- Agent 會以哪些關鍵字、分類、狀態、日期或 Relation 查詢？
- RAG 擷取單筆資料時，名稱與摘要是否足以先判斷相關性？
- 來源是否能回到原始證據？資料是否能判斷新鮮度與審核狀態？
- 不同實體是否已拆分並以 Relation 連接，而非全部塞入單一 Database？
- 每個欄位是否有實際用途？移除它會失去哪一個可驗證的能力？
- 預設 View 是否服務最常見工作流，而不是只展示所有欄位？

若這些問題仍有會改變 Schema 的未知，先詢問；若只是不影響結構的細節，使用明確標示的假設並在交付時揭露。
