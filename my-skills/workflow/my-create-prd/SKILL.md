# my-create-PRD

## 目的

將零散想法轉成可決策、可實作、可驗收的繁體中文 PRD。主動找出資訊缺口並進行多輪訪談，不以猜測填補會改變產品方向的關鍵需求。

## 工作流程

### 1. 蒐集現有資訊

- 讀取使用者提供的文件、連結、研究、數據與既有規格。
- 先整理「已確認、待確認、暫定假設、互相衝突」四類資訊。
- 若使用者要求修改既有 PRD，保留有效內容，指出缺口與衝突後再重寫。
- 只有在使用者要求、引用外部資料或資訊具有時效性時才查證外部來源，並區分事實、推論與假設。

### 2. 主動進行多輪需求訪談

- 資訊不足時主動提問；每輪優先提出 1 至 3 個最影響範圍、成本、風險或驗收的問題。
- 問題需具體、容易回答；必要時附 2 至 3 個互斥選項與其影響，但不得替使用者做重大產品決策。
- 每輪收到回答後，更新已確認內容與剩餘缺口，再進入下一輪。
- 發現矛盾時先指出衝突、說明影響並要求裁決。
- 使用者暫時無法回答時，可提出明確標示的暫定假設、負責人與驗證期限；不得把假設寫成既定事實。
- 持續訪談，直到通過「PRD 完整性閘門」，或使用者明確要求先產出草案。

### 3. 通過 PRD 完整性閘門

定稿前確認下列項目都有可執行答案：

- 問題、背景、目標使用者與使用情境清楚。
- 目的、可衡量目標、成功指標及目標期限清楚。
- 範圍內、範圍外、優先級與版本界線清楚。
- 功能需求、非功能需求、資料或內容需求清楚。
- 必要事項、禁止事項與產品原則清楚。
- 主要流程、例外、錯誤與邊界情境清楚。
- 每項 P0／必要需求都有可驗證的驗收標準。
- 相依性、限制、風險、假設、待決事項與負責人清楚。
- 發布條件、回滾或停止條件清楚。
- 不同 Agent 不需猜測關鍵決策即可拆解與執行工作。

若仍有阻擋實作的未知事項，繼續訪談；若使用者要求先出草案，須在文件開頭標示 `狀態：草案／資訊未完整`，並集中列出未決問題。

### 4. 撰寫並交付 PRD

- 使用繁體中文；保留必要且更清楚的英文技術名詞。
- 使用短句、明確動詞與一致術語，避免空泛詞彙，例如「友善」、「快速」、「最佳化」而沒有量化標準。
- 為需求編號，例如 `FR-001`、`NFR-001`、`AC-001`，並標示 P0／P1／P2 優先級。
- 將需求與驗收標準建立明確對應。
- 大型 PRD 存為 `PRD-<產品或功能名稱>.md`；修改既有 PRD 時優先更新原檔，除非使用者指定另存。

## PRD 必備結構

### 1. 文件摘要

- 名稱、狀態、版本、日期、負責人與利害關係人
- 一段式摘要

### 2. 背景與問題

- 現況、問題證據、為何現在要做
- 目標使用者、工作情境與主要痛點

### 3. 目的

- 說明為何要做、要創造什麼價值，以及與產品或組織策略的關係。
- 目的描述方向，不冒充可衡量目標。

### 4. 目標與成功指標

- 定義可衡量、具期限的成果目標與基準值。
- 同時列出非目標，避免範圍擴張。
- 指標至少包含名稱、定義、目前值、目標值、期限與資料來源；未知值標示待補。

### 5. 產品原則

- 列出面對取捨時的判斷準則，並說明優先順序。
- 原則需能指導決策，例如安全高於便利、資料正確高於表面完成。

### 6. 範圍與版本

- 範圍內、範圍外、P0／P1／P2、第一版與後續版本。
- 清楚說明不承諾的內容。

### 7. 需求

- 功能需求：角色、觸發條件、行為、輸入、輸出、狀態與例外。
- 非功能需求：效能、可用性、可及性、安全、隱私、相容性、觀測性與維運要求。
- 資料與內容需求：來源、欄位、權限、保存、同步、錯誤與空狀態。
- 使用者流程與必要介面行為；有設計稿時附連結，不虛構不存在的設計。

### 8. 必要的

- 集中列出不可缺少的 P0 能力、法規／安全條件、資料要求與發布前置條件。
- 每一項都需對應需求編號與驗收標準；缺少任一項即不得宣告完成或發布。

### 9. 禁止的

- 集中列出不可採用的行為、技術捷徑、資料處理方式、UX 模式與範圍外實作。
- 說明禁止原因及違反時的停止、修正或升級處理方式。

### 10. 驗收標準

- 使用 Given／When／Then 或同等明確格式。
- 涵蓋主要成功流程、失敗流程、權限、邊界與回歸風險。
- 驗收結果必須可觀察，不得只寫「正常」、「完成」或「符合預期」。

### 11. 相依性、限制與風險

- 列出外部系統、團隊、資料、法規、時間、預算與技術限制。
- 每項主要風險需有機率、影響、緩解措施、負責人與觸發條件。

### 12. 假設、待決事項與發布

- 假設需附驗證方法與失效影響。
- 待決事項需附負責人與決策期限。
- 定義發布門檻、分階段策略、監測方式、停止條件與回滾方式。

## 必須遵守

- 必須使用繁體中文整理描述與 PRD 主體。
- 必須清楚分開目的、目標、需求、原則、必要事項與禁止事項。
- 必須標示所有未知、假設、衝突與資料缺口。
- 必須讓必要需求具備編號、優先級及可驗收條件。
- 必須在定稿前執行完整性閘門，並回報文件狀態。
- 必須以使用者最新確認的決策為準，保留決策變更脈絡。

## 禁止事項

- 禁止把推測、慣例或市場常識寫成使用者已確認的需求。
- 禁止為了快速完成而略過會改變範圍、成本、安全或驗收的問題。
- 禁止只列功能名稱，卻沒有行為、條件、例外與驗收方式。
- 禁止混淆目的與目標，或使用不可衡量的成功指標。
- 禁止在未揭露資訊缺口時宣稱 PRD 已完整、可實作或可發布。
- 禁止擅自擴張至未授權的產品、平台、整合或發布範圍。

## 完成回報

交付時簡短列出：

1. 文件路徑或完整 PRD。
2. 文件狀態：草案、待確認或已通過完整性閘門。
3. 已確認的重要決策。
4. 尚未解決的問題、風險與下一位負責人。
